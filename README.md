# DJO Validation System

A Streamlit MVP, backed by a modular Python service layer, for validating
Brazilian/MERCOSUL **Declaração Juramentada de Origem (DJO)** documents
against the **ACE 18** rules-of-origin regime — OCR → structured data →
8 business-rule checks → ACE 18 NCM lookup → the official origin-rule
flowchart → a plain-language summary, generated by either **Gemini** or
**Groq**.

See [ARCHITECTURE.md](ARCHITECTURE.md) for the full system design,
response schema, and how to extend it.

## Quick start

```powershell
# 1. Install dependencies (a virtual environment is recommended)
pip install -r requirements.txt

# 2. Configure your API keys
copy .env.example .env
# then edit .env and set GEMINI_API_KEY and/or GROQ_API_KEY, plus
# LLMWHISPERER_API_KEY (needed regardless of which LLM provider you use —
# it's what turns the uploaded PDF into text in the first place)

# 3. Run the app
streamlit run app.py
```

Open the URL Streamlit prints (default `http://localhost:8501`).

## Using the app

1. **Upload a DJO PDF** — sample documents are available under
   `dados/djos/`.
2. **Select the product category** — Industrial, Game / Assortment, or
   Automotive. This is never guessed from the document; automotive
   products are explicitly out of scope for the ACE 18 origin-rule
   flowchart and will come back `NOT_APPLICABLE`.
3. **Select the LLM provider** — Gemini or Groq. This only affects which
   API writes the plain-language summary and resolves a small number of
   free-text rule conditions the deterministic engine can't classify —
   it never affects the validation result itself (PASS/FAIL, the
   applicable origin rule, etc. are always decided by Python).
4. If you pick **Groq**, a **Model** dropdown appears — populated live
   from the Groq API when `GROQ_API_KEY` is set, or a curated fallback
   list otherwise. Gemini has a similarly curated model list.
5. Click **Validate DJO**. Processing takes anywhere from a few seconds
   to about a minute (OCR + one or more LLM calls).
6. For a **Game / Assortment** product, if the flowchart can't proceed
   without knowing whether the product complies with Article 14 (Games &
   Assortments), the app will ask that question directly and re-run the
   evaluation once you answer.

The result view shows the DJO status, the applicable ACE 18 origin rule,
a table of the 8 individual business-rule checks, the full decision
sequence from the flowchart (expand any step to see why it was decided
that way), and the LLM-generated explanation — clearly labeled with which
provider/model produced it. A "Raw structured response" section at the
bottom shows the exact JSON the service layer returned, useful for
debugging or for a future frontend/API integration.

## Running without the UI

```powershell
python examples\run_local.py "dados\djos\DJO 3 (1).pdf" industrial
python examples\run_local.py "dados\djos\DJO 3 (1).pdf" industrial --llm-provider groq --llm-model openai/gpt-oss-120b
```

## Tests

```powershell
python -m pytest              # offline, no API keys needed
python -m pytest -m integration   # + one real end-to-end test (needs real API keys in .env)
```

## Project layout

```

tests/             — pytest suite
examples/          — non-UI usage example
dados/             — sample DJO PDFs + the ACE 18 rules cache
```

## Security notes

- API keys (`GEMINI_API_KEY`, `GROQ_API_KEY`, `LLMWHISPERER_API_KEY`) are
  read from environment variables only — never hard-coded, never logged,
  never included in the app's output or in `validate_djo_pdf`'s response.
- `.env` is git-ignored (see `.gitignore`); only `.env.example`, with
  empty placeholder values, is meant to be committed.
- Errors are always surfaced as a clean `{type, message}` object — the
  app and the service layer never expose a raw Python traceback.
